AI Investigation Engine: field guide

How the project works, the order it was built in, and why each choice was made. For an iOS developer new to AI engineering. Status: 27 October 2026.

1. The big picture

Two pipelines. Slow work happens once when documents change; fast work happens per question.

Ingestion: when a document is added, changed or deleted

File / record.txt .md .json .pdf, or a HotpotQA passage
Parsesentences + metadata
FingerprintSHA-256; duplicates stop here
Registrysave document, version, status
Chunkfixed and sentence strategies
Embed → QdrantMiniLM vectors (ONNX)
Words → BM25keyword index

Investigation: for every question

Questionfrom UI or API
PlanLLM lists ≤ 3 searches
Search toolvector + keyword, fused by RRF
Decidesearch again, or answer citing E1…En
Validateour code checks citations
Resultanswered · conflict · insufficient

The three stores they share

Registry (SQLite / Postgres): the truth. Documents, versions, sentences, chunks.
Qdrant: vectors. Rebuildable from the registry.
BM25 (in memory): keyword index. Rebuilt from the registry at start-up in 3.7 s.

3. Build roadmap

Each step depends only on the steps above it, the same rule as building components before screens. Risky unknowns (is the data usable? can we reach 50,000?) come early.

  1. 0

    Environment and requirements

    Python 3.12 .venv, project manifest, the list of mandatory items.

    Why first: everything runs inside it, and the list defines "done".

    pyproject.tomlCLAUDE.md
  2. 1

    Inspect the data

    Count questions, passages, empties, duplicates, broken labels.

    Why now: the data decides the design. Found 73,700 passage copies → 66,581 distinct, 26 duplicates, 1 broken label.

    dataset-inspection.pymeasured counts
  3. 2

    Define a record and its id

    One record = one distinct passage; hp- + hash of title; sentence numbers kept.

    Why now: ids flow into chunks, vectors, citations and evaluation. Like choosing primary keys before shipping.

    hotpotqa.py
  4. 3

    Models and registry

    Sentence, Document, Chunk, Status; two SQL tables.

    Why now: the shared language of every later module.

    models.pyregistry.py
  5. 4

    Parsers and document lifecycle

    TXT/MD, JSON, PDF; add, update, delete, duplicates, retry.

    Why now: the write order keeps three stores consistent. Easier to get right before 66,000 documents exist.

    parsers.pyingestion.pyfailure + retry tested
  6. 5

    Two chunkers

    Fixed 64-word windows (16 overlap) and whole-sentence packing (≤ 64 words).

    Why now: chunks are what gets searched; the comparison is required.

    chunking.py
  7. 6

    Our ranking algorithms

    BM25 keyword scoring and Reciprocal Rank Fusion.

    Why now: pure functions, no dependencies, testable by hand. A custom algorithm is required.

    bm25.pyfusion.pyhand-computed tests
  8. 7

    Embeddings, Qdrant, hybrid search

    Semantic, keyword and hybrid modes in one search().

    Why now: needs chunks and the ranking code.

    embeddings.pyvector_store.pyretrieval.py
  9. 8

    Load 66,581 records

    Batches of 1,024, resumable, with a reconciliation report.

    Why now: scale is the biggest risk; real data then feeds every later step. Took 6.3 minutes.

    bulk.py0 failed, counts match
  10. 9

    LLM client and investigation pipeline

    Plan, search tool, decide, second chance, validate; Groq and Gemini clients with retries, daily-quota detection and fallback models.

    Why now: sits on top of search. Built against a fake LLM first, so behaviour is tested without cost.

    llm.pyinvestigate.py
  11. 10

    API, then UI

    FastAPI endpoints; one HTML page (first Streamlit, later replaced) talks to them over HTTP like an app to a backend.

    Why now: they only expose what already works.

    api.pyweb/index.html
  12. 11

    Evaluation

    46 questions in 5 categories; retrieval on 500 more.

    Why now: you can only measure a working system.

    evaluation.pytwo runs measured
  13. 12

    Load the cloud stores

    Same bulk loader, pointed at Neon and Qdrant Cloud, one chunk strategy to fit free storage.

    Why now: the host can change; the data should not. Took 8 minutes; counts matched.

    ingest_hotpotqa.py130,854 = 130,854
  14. 13

    Fit a 512 MB server

    Measure first, then cut: ONNX embeddings, compact BM25, plain-HTTP Qdrant, one process.

    Why: free hosts give 512 MB; the app needed about 1.1 GB. Every cut was proven to give identical results.

    embeddings.pybm25.pyvector_store.py~1,105 → 335 MB
  15. 14

    Deploy on Render

    GitHub push → Render builds the Docker image → public HTTPS URL. Secrets typed into Render, never in Git.

    Why last: deploying unfinished work means redeploying again and again. Hugging Face (needs PRO) and Oracle (no capacity) were tried first.

    Dockerfilerender.yamllive, data survived restart

4. Keywords

Filter by layer or type to search. Each card has the plain meaning and an iOS comparison where one helps.

Corpus

All documents the system can search. Ours: 66,581 passages + 17 synthetic.

Source record

One independent document. The "50,000" counts these, not questions or chunks.

Metadata

Facts about a document that are not its text: title, pages, version, status.

Normalisation

Removing unimportant differences before comparing. We collapse whitespace.

Hash / SHA-256

A 64-character code from text. Same text, same code: exact duplicate.

a file checksum

Deduplication

Keep repeated content once; copies point to the original.

Provenance

Where text came from: doc id, version, sentence numbers, page. Citations need it.

Synthetic data

Test data we wrote; always labelled synthetic.

Chunk

A small piece of a document. Search returns chunks, so the LLM reads only what matters.

cell reuse: small pieces, not the whole list

Embedding

384 numbers describing a text's meaning. Similar meaning → nearby numbers.

Vector

That list of numbers. Vector search = find the stored vectors nearest the question's.

Cosine similarity

Closeness as an angle: 1 same meaning, 0 unrelated.

Vector database

A database that finds nearest vectors fast. Ours: Qdrant.

Semantic search

Search by meaning. Good with paraphrases, weak with exact ids and names.

Keyword search

Search by matching words. Good with INC-7781 and names, blind to synonyms.

Stop words

Common words ("the", "of") ignored by keyword search.

Inverted index

Word → list of chunks containing it. Skips everything irrelevant.

a dictionary keyed by word

BM25

Keyword scoring: rare words count more, repeats help less and less, long chunks are penalised a bit. Our own code.

Hybrid search

Semantic + keyword together, each covering the other's blind spot.

RRF

Merges ranked lists by adding 1 / (60 + rank). Uses positions, not scores. Our own code.

Top-K

The first K results.

Re-ranker

A slower second model that re-scores the top results. Not built (bonus).

LLM

A model that writes text from instructions and context. Ours: gpt-oss-120b on Groq.

Token

The unit an LLM reads and bills in, about ¾ of a word.

Context window

How much text fits in one request. Why we send ≤ 700 characters per evidence item.

Prompt

What we send: fixed rules (system) + question and evidence (user).

Hallucination

A plausible statement not supported by the evidence. The design exists to block it.

RAG

Retrieval-Augmented Generation: search first, then answer from what was found.

Grounding

Making the answer depend only on the supplied evidence.

Multi-hop

Needs two facts where the second depends on the first.

Citation

Evidence id (E1…) on a claim. Fake ids are dropped by our code.

Abstention

Saying "insufficient evidence" instead of guessing.

Tool calling

The LLM asks the program to run a function (our search) via a JSON action we validate.

a delegate callback the app chooses to honour

JSON mode

Forces the LLM to reply with valid JSON so code can parse it.

Codable decode

Temperature

Randomness. We use 0 for repeatable answers.

Rate limit

Provider caps: 1,000 requests/day, 8,000 tokens/minute on your key. HTTP 429 → wait and retry.

Prompt injection

Document text that tries to command the LLM. Our rules say evidence is data.

Gold / ground truth

The known right answer and right documents for a test question.

Recall@K

Share of needed documents found in the top K.

MRR

1 ÷ position of the first right document, averaged. Rewards ranking it first.

EM and F1

Exact answer match, and partial credit for shared words.

Answer correctness

Right answer; or "insufficient" when unanswerable; or "conflict" citing both sides.

Citation precision

Share of cited documents that are actually relevant.

Configuration

One combination of settings. We compare two.

PaaS vs IaaS

Render runs your app for you (platform); Oracle rents you an empty server you manage (infrastructure).

App Store distribution vs running your own Mac mini server

Container

A packaged, runnable copy of the app with its Python and libraries, built from the Dockerfile.

an archived, signed build

Stateless server

Keeps no data of its own, so it can be restarted or replaced; data lives in Neon and Qdrant.

Cold start

The wait while a sleeping free-tier server starts again: here about 1.5–2 minutes.

app launch from a killed state

RSS (resident memory)

Memory the process really uses; what the 512 MB limit counts. /health reports it.

ONNX

A portable format for running a trained model without PyTorch. Same model, same vectors, far less memory.

like shipping a compiled Core ML model instead of the training code

Rolling quota

A limit counted over the last 24 hours, not reset at midnight; capacity returns gradually.

Fallback model

A second LLM used when the first one's quota is gone; the answer says which one replied.

Environment secret

A key typed into the host's settings (Render), read at start-up, never stored in Git.

a value injected by your CI, not in the repo

7. One question, step by step

"When did the fire alarm sound at the Pier 9 warehouse?" Two sources disagree, so the right result is a conflict.

  1. 1
    API receives it

    POST /investigate; Pydantic rejects empty or too-long questions.

  2. 2
    Plan

    LLM returns up to 3 search queries as JSON. If the call fails, we search the question alone.

  3. 3
    Search tool

    Embed → Qdrant top 50. Tokens fire alarm sound pier 9 warehouse → BM25 top 50. RRF → best 5. Text loaded from the registry.

  4. 4
    Evidence

    E1 Fire dispatch log (21:40) · E2 Harbour Daily (22:35) · E3 Insurer notice · then unrelated fires.

  5. 5
    Decide

    LLM replies {"action": "answer", "status": "conflict", …} citing E1 and E2, or {"action": "search"} for more.

  6. 6
    Second chance

    Only if it said "insufficient": it must name one more search first.

  7. 7
    Validate

    Unknown citations dropped; uncited answer → insufficient; conflict needs two cited items.

  8. 8
    Result

    Status, answer, claims, conflicts, all evidence and the full trace. The UI highlights cited sentences in the source.

12. Next project checklist

  1. List requirements and what will prove each one.
  2. Inspect the data with a throwaway script before designing.
  3. Decide what one record is and its id; keep sentence and page positions.
  4. One store is the truth; every index can be rebuilt from it.
  5. Fixed write order + statuses, so failures leave nothing half-searchable.
  6. Start with keyword search as the baseline; add semantic; fuse.
  7. LLM behind one tiny interface; develop against a fake; validate its JSON in code.
  8. Build evaluation early: retrieval metrics first (no LLM cost), answers second.
  9. Change one setting at a time and keep the numbers and failure examples.
  10. Deploy last, with persistent storage and secrets outside the code.
